# ADK 2.3.0 and chapter 3: publisher agent and human handoff

Date: 2026-10-14
Status: approved 2026-10-14 by the maintainer's standing instruction to
publish the next chapters without further questions. The decisions below were
made by the agent and are open to review.

## Purpose

Two things in one release, `v5`:

1. The upgrade to ADK 2.3.0 that the specs of 2026-10-13 announced.
2. Chapter 3: an agent that takes a listing draft a person approved, checks
   it, and writes a ready-to-post package. It never posts.

After chapter 3 the learner can enforce a rule in code before a model runs,
write a tool that trusts nothing it is told, and state what a correct run
looks like as eval cases.

The reasons are in
[ADR 0001](../../adr/0001-model-access-through-adk.md), section "ADK 2.3.0
and chapter 3".

## Scope

In scope:

- ADK 2.3.0 on `main` and on every chapter branch, with the refreshed guides.
- An override for one transitive dependency with an open advisory.
- Corrections in chapter 2 where it announced `adk eval`.
- Branches `chapter-03-starter` and `chapter-03-solution`, the chapter 3
  criteria, the chain of seven branches, and the texts on `main`.
- Release `v5` on all six chapter branches, and the push.

Out of scope:

- Posting a listing. No chapter does that.
- A status after `freigegeben`, several images per listing, and price or
  category rules beyond what the draft schema holds.
- Chapter 4.
- A fix for `adk eval`. It is upstream's to fix.

## Decisions

| Topic | Decision |
|---|---|
| ADK version | `@google/adk` and `@google/adk-devtools` at exactly `2.3.0` |
| Evals | Through `runEvals`, called by `scripts/run-evals.ts`. `adk eval` cannot load an agent file in 2.3.0 (ADR 0001, decision 8) |
| Where evals are used | In chapter 3 only. Chapter 2 keeps `session:check` (decision 9) |
| Approval gate | A before-agent callback. A draft that is not `freigegeben` never reaches the model (decision 10) |
| Tool arguments | `prepare_listing` takes none. The draft path comes from the session state |
| What the tool trusts | Nothing. It reads the draft file again and checks it |
| What the model does | It reads the listing critically and writes the handoff note. It calls the tool in every case |
| Package | A JSON file beside the draft, `<name>.listing.json`: the fields, the image, a checklist. It is overwritten on every run |
| Images | One, the `image` field of the draft, resolved from the draft's folder |
| Log output of `adk run` | The entry file sets the level for the agent's ADK, and the npm scripts pass `--log_level warn` for the CLI's |
| Dependencies | `overrides` sets `tedious` to `^20.3.7`, which removes `sprintf-js` |

Run before this spec was written, on ADK 2.3.0: the chapter 1 and 2 offline
tests, unchanged; the chapter 3 reference solution against its offline test,
with six deliberate mistakes; the eval set through `runEvals` with a scripted
model and live; and `npm run agent:publisher` live. The evidence is in
`docs/debugging/2026-10-14-adk-2.3.0-and-chapter-03/` on the maintainer
branch.

## Chapter 3

### Architecture

```
npm run agent:publisher
  adk run adk/publisher_agent.ts --replay examples/replays/publisher-agent.json
          --save_session --session_id publisher-agent --log_level warn
    └─ publisher_agent                    LlmAgent
         ├─ before-agent callback         requireApprovedDraft
         │    reads draft_path from the state, reads the draft
         │    not approved → answers itself, the model is not called
         │    approved     → stores the listing in the state
         └─ prepare_listing               no arguments
              reads the draft again, checks the rules
              → examples/drafts/approved.listing.json, or the problems

npm run eval:publisher                    scripts/run-evals.ts → runEvals
  examples/evals/publisher.evalset.json   the learner's eval cases
```

### The package

```json
{
  "title": "Nintendo Game Boy Classic DMG-01, grau",
  "price": 85,
  "currency": "EUR",
  "category": "Handheld Consoles",
  "condition": "used",
  "description": "Verkaufe meinen originalen Nintendo Game Boy Classic …",
  "images": ["../photos/game-boy.jpg"],
  "checklist": ["Compare the photo with the title and the description.", "…"]
}
```

### `scripts/test-offline-chapter-03.ts` (provided)

All cases use the scripted model and a temp directory. No API key.

10. `parseDraft`: every field of the approved example; the same with `\r\n`;
    a `DraftFormatError` that names the problem for six broken files.
11. `findProblems`: none for a valid draft; 65 characters allowed and 66 not,
    with both numbers in the message; a missing image and a folder as image;
    a status that is not approved; all three at once.
12. `prepareListing`: the package beside the draft with exactly the expected
    content; an error result that names the field for four rejected drafts
    and three unusable states; no package for a rejected draft.
13. The gate: for a draft that is not approved, one that cannot be read, and
    no draft path, the model is not called and no tool runs.
14. The agent: the listing is in the state and in the instruction; exactly
    one tool, without arguments; the package is written.
15. The eval set: it has the three kinds of case with the right expected
    calls, and every case passes through `runEvals`.
